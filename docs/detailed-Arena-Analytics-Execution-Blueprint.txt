Concrete Execution Blueprint (No Code)

1. API Contracts Layer
   1.1 Contract strategy
   Keep the current dashboard contract intact for backward compatibility with Index.cshtml.
   Introduce a versioned analytics contract family for enterprise sections.
   Use additive evolution only in the first rollout wave.
   1.2 Endpoint blueprint
   Aggregated admin analytics endpoint
   Purpose: one-call dashboard hydration for executive landing.
   Scope: executive summary, financial overview, user analytics, operational analytics, growth metrics, alerts.
   Filters: fromDate, toDate, timezone, granularity, compareMode.
   Output: sectioned payload with metadata block containing generatedAtUtc, timezoneApplied, freshness, dataQualityFlags.
   Focused drilldown endpoints
   Membership analytics endpoint:
   Active vs inactive, renewals due, expiring windows, churn/retention rollups.
   Revenue analytics endpoint:
   Revenue trend, revenue by plan, revenue by payment method, payment failure trend.
   Operational analytics endpoint:
   Attendance trend, peak-hours heatmap, booking funnel, no-show trend.
   Engagement analytics endpoint:
   At-risk members list, AI adoption trend, intent mix.
   Alerts endpoint:
   Expiring bursts, attendance drop alerts, payment anomaly alerts.
   Governance endpoints
   Analytics metadata endpoint:
   Schema/version, available metrics, blocked metrics, freshness SLA.
   Health endpoint:
   Last snapshot build status and lag.
   1.3 Authorization model alignment
   Harden all admin analytics routes to Admin role policy.
   Align MVC admin access model with API role boundaries currently configured in Program.cs.
   Treat unsecured analytics-adjacent routes as a precondition task before rollout.
2. Query Model Layer
   2.1 Read model split
   Real-time query group
   KPI cards that need near-live values:
   today attendance
   active subscriptions
   expiring in next 7 days
   Source pattern: direct transactional tables with narrow predicates.
   Historical query group
   Trend and segmentation charts:
   monthly revenue, attendance trends, heatmap, churn/retention trend
   Source pattern: pre-aggregated fact tables at daily and hourly grain.
   2.2 Canonical metric fact model
   FactMemberDaily:
   activeMembers, inactiveMembers, newMembers, atRiskMembers
   FactSubscriptionDaily:
   activeSubs, expiredSubs, cancelledSubs, renewalsCount, expiring7dCount, expiring30dCount
   FactRevenueDaily:
   grossRevenue, paidCount, failedCount, avgRevenuePerMember
   FactAttendanceHourly:
   checkIns by dayOfWeek/hour, distinctMembers, utilization proxy
   FactBookingDaily:
   totalBookings, confirmedBookings, attendedBookings, noShows, cancellations
   2.3 Event capture requirements
   Add lifecycle events for:
   subscription state transitions
   booking state transitions
   payment attempts and outcomes
   These events are required for reliable churn and renewal analytics.
   2.4 Query ownership boundaries
   Legacy dashboard stays in existing service path:
   DashboardService.cs
   New analytics queries move to dedicated analytics read services (separate from transactional command services).

5.1 Tiered TTL policy
Real-time cards
TTL: 30 to 90 seconds
Invalidate on payment completion, attendance check-in, subscription status change.
Near-real-time charts
TTL: 5 to 15 minutes
Invalidate on hourly snapshot completion.
Historical trends
TTL: 30 to 60 minutes
Invalidate on daily snapshot completion.
5.2 Cache key strategy
Key dimensions:
section
date range
timezone
granularity
filter set hash
Include contract version in key namespace.
5.3 Cache correctness controls
Stamp payload with freshness metadata.
Serve stale-if-error for non-critical sections.
Never serve stale for financial totals beyond SLA threshold. 6. Visualization Backlog Layer
